# Azure configuration: portal walkthrough

This guide describes the same resources as `infra/main.bicep` and `infra/apim.bicep`. The Function exposes REST operations; API Management can expose selected operations as MCP tools. The Function itself does not implement MCP.

## Prerequisites

- An Azure subscription with permission to create the resources and role assignments listed below.
- Azure CLI, Bicep, Node.js 22, and Azure Functions Core Tools v4.
- A Power Platform environment and Copilot Studio access to connect an MCP server.

## Create the Azure resources

| Portal step | Resource or setting in Bicep |
| --- | --- |
| Create a Standard general-purpose v2 storage account; disable public blob access and shared-key access; require HTTPS and TLS 1.2. | `infra/main.bicep`: `storage` |
| Create a private Blob container named `function-packages` for Flex Consumption deployment packages. | `infra/main.bicep`: `storage/blobServices/containers` |
| Create a Flex Consumption plan (`FC1`) and Linux Function App using Node.js 22. Enable system-assigned managed identity and HTTPS-only traffic. | `infra/main.bicep`: `functionPlan`, `functionApp` |
| Give the Function identity Blob Data Owner, Queue Data Contributor, and Table Data Contributor roles on the storage account. Configure host storage to use managed identity. | `infra/main.bicep`: `blobRole`, `queueRole`, `tableRole`, `functionApp/appSettings` |
| Create a Free-tier Static Web App. Deploy the contents of `web/dist` with the Static Web Apps CLI deployment token. | `infra/main.bicep`: `staticWebApp`; `infra/deploy.ps1` |
| Create API Management on the Developer tier, setting a publisher name and contact email. | `infra/apim.bicep`: `apim` |
| Add a secret named value containing the Function host key. | `infra/apim.bicep`: `functionKeyValue` |
| Import the Function's OpenAPI 2.0 definition twice: public `weather` and subscription-protected `copilot-weather` REST APIs, each with location search, current weather, daily forecast, and running assessment operations. | `infra/apim.bicep`: `publicApi`, `copilotApi` |
| Attach CORS, per-IP rate-limit, and Function-key forwarding policies to both APIs. | `infra/apim.bicep`: API policies; `infra/apim-policy.xml` |
| After deploying the REST API, create an MCP server from the `Weather for Copilot Studio` API and select the operations exposed as tools. | API Management portal; MCP server is created after deployment, not by `infra/apim.bicep` |

The backend needs a Function key, not the Function App master key. The deployment script reads the default host Function key only after publishing the code, supplies it to Bicep as a secure parameter file outside the repository, and removes the temporary file after APIM deployment.

## Deploy or update

From the repository root, sign in with Azure CLI and run:

```powershell
az login
az account set --subscription "<subscription-id-or-name>"
az bicep install
.\infra\deploy.ps1 -ResourceGroupName rg-sd-weather-demo -Location westeurope -PublisherEmail you@example.com
```

The script deploys the infrastructure, publishes the TypeScript Function, configures APIM and deploys the web app. If rerunning after a code or OpenAPI change, it republishes the Function and updates the APIM API definitions. Reapply the manual MCP operation-template workaround below after importing the API again. The existing MCP server may need its selected tools refreshed in the portal after the API operations change.

The local `api/local.settings.json` should have `FUNCTIONS_WORKER_RUNTIME` set to `node` for Core Tools. Do not add that setting to the Flex Consumption Bicep app settings; Flex configures the runtime through `functionAppConfig.runtime`.

## Create the MCP server in API Management

1. In the Azure portal, open the API Management instance and go to **APIs → MCP Servers → Create MCP server → Expose an API as an MCP server**.
2. Select **Weather for Copilot Studio** as the backend API, after applying the operation templates below.
3. Select `SearchLocations`, `GetDailyForecast`, and `AssessRunningConditions` as tools; optionally also select `GetCurrentWeather`.
4. Enter a display name, name, and short description. For subscription-based access, associate both the MCP server and **Weather for Copilot Studio** REST API with the same protected product, enable **Subscription required** on both resources, and use an active subscription to that product. A subscription scoped to a different API or product may be rejected during tool execution. Do not use the built-in all-access subscription for an agent.
5. Open the MCP server and copy its **Server URL**. It is generated by APIM and ends with `/mcp`; it is not the REST API URL.

APIM exposes the selected REST operations as MCP tools. APIM MCP currently supports tools, not MCP resources or prompts. Refer to the current [APIM MCP documentation](https://learn.microsoft.com/azure/api-management/export-rest-mcp-server) for availability and portal changes.

### Configure REST operation templates for MCP

In the tested APIM setup, generated MCP calls with optional query parameters produced malformed values such as `Barcelona?country=Spain`. Direct REST calls worked, while MCP forecast/assessment calls returned `invalid_date` for a valid date. This was not a Copilot Studio prompt or Function date-validation problem.

The verified workaround is to include all query parameters in the operation URL template on the **Copilot REST API only**. Open **APIs > APIs > Weather for Copilot Studio > Design**, select each operation, and edit **Frontend**:

| Operation | URL template |
| --- | --- |
| Current weather | `/weather?city={city}&country={country}&admin1={admin1}` |
| Daily forecast | `/forecast?city={city}&date={date}&country={country}&admin1={admin1}` |
| Running assessment | `/running-assessment?city={city}&date={date}&country={country}&admin1={admin1}` |
| Location search (unchanged) | `/locations?query={query}` |

Keep only one `?` per template and use `&` between parameters. Remove duplicate `country` and `admin1` entries from **Query parameters**, keeping their entries under **Template parameters**, and save. This makes these qualifiers required by APIM on the affected Copilot operations. First search for the location and supply the returned values in every subsequent call; if no region is available, this workaround needs further adaptation rather than an invented region.

The Function and public web API still support optional qualifiers. The checked-in OpenAPI definitions retain that REST contract; this workaround is a manual, Copilot-API-only portal adjustment, not an automated deployment feature. Recheck it after redeploying or reimporting the API. If the generated tool schema is stale, refresh the MCP tools and the agent's tool metadata.

## Connect the MCP server to Copilot Studio

1. Open the agent in Copilot Studio and go to **Tools → Add a tool → Add → Model Context Protocol (MCP)**. Labels can vary by UI language and version.
2. Enter the MCP server name, a concise description, and the Server URL copied from APIM.
3. Configure the authentication used by the APIM MCP server. For an APIM subscription key, choose API key authentication with **Header** type and header name `Ocp-Apim-Subscription-Key`; use an active subscription whose product includes both the MCP server and the source REST API. Enter the key only in the connection's credential field, never in agent instructions or the server URL.
4. Create or select the connection and add the server to the agent.
5. Test a location lookup and then ask: “Should I go running in Barcelona tomorrow?”

The optional `deploy-output/copilot-weather.openapi.json` file is for the separate custom connector integration path. It is not the URL or schema used by the direct MCP onboarding wizard. See [Copilot Studio's MCP connection guide](https://learn.microsoft.com/microsoft-copilot-studio/mcp-add-existing-server-to-agent).

### Suggested agent instructions

Use the actual tool names shown in your MCP tool list; APIM can generate names from the operation summaries.

```text
Use the MCP weather tools as the source for weather answers.
Search locations first. Keep city, country, and admin1 as separate fields,
using the returned location values. Ask the user when the location is ambiguous;
do not infer it from their personal name.
Send all location fields required by the tool schema.
Use YYYY-MM-DD dates within the supported range. Resolve today/tomorrow
using the current date and the selected location's time zone.
For running questions, use the running-assessment tool and report its
recommendation, thresholds, reasons, and demo disclaimer.
Inspect the returned content for errors even if isError is false.
If valid arguments produce a technical error, report it without guessing
the cause, trying arbitrary variants, or silently falling back to web search.
Do not describe a forecast-only interpretation as a completed running assessment.
```

### Validate execution, not only discovery

Test `initialize`, `tools/list`, and an actual `tools/call`. In the observed APIM responses, the HTTP status was `200` and `isError` was `false` even when the tool content contained a REST `401` or `invalid_date` error. Inspect the tool's JSON text and verify it contains the expected location, forecast, or assessment fields.

For temporary anonymous diagnostics, **both** the MCP server and the source REST API must allow requests without a subscription. Changing only MCP Settings can leave initialization working while every tool call fails with a missing-key error. Restore protection on both resources after the test; do not leave the demo anonymously accessible by accident.

## REST paths and assessment behavior

The public APIM API path is `weather`; operation paths are:

| Operation | Public APIM path |
| --- | --- |
| Current weather | `/weather/weather?city=Barcelona&country=Spain&admin1=Catalonia` |
| Search locations | `/weather/locations?query=Lleida` |
| Daily forecast | `/weather/forecast?city=Barcelona&date=YYYY-MM-DD&country=Spain&admin1=Catalonia` |
| Running assessment | `/weather/running-assessment?city=Barcelona&date=YYYY-MM-DD&country=Spain&admin1=Catalonia` |

For the Copilot-facing REST API, replace the first `/weather` path segment with `/copilot-weather`. The MCP URL is separate and is shown on the MCP server resource.

Forecast dates are limited to today and the following six days. If the geocoder finds several exact city-name matches, the Function returns `409` with suggestions; use the `country` or `admin1` query parameter to disambiguate. The city resolver treats the Spanish exonym `Lérida` as the provider's `Lleida` search name. The running assessment uses these demo limits: minimum temperature 5 °C, maximum temperature 30 °C, precipitation 2 mm, and wind speed 25 km/h. It is a simple sample rule, not safety or medical advice.

## Common failures

| Symptom | Likely cause | Check |
| --- | --- | --- |
| Function deployment or startup fails on storage access. | Managed-identity role assignments haven't propagated, or Flex deployment storage isn't configured. | Check the Function identity's storage data roles and `functionAppConfig.deployment.storage`; retry after role propagation. |
| APIM returns `401` or `403` from the Function backend. | The named value is missing or the stored key is not a host/function key. | Refresh the Function host key, update the secret named value, and test the backend from APIM. |
| Browser calls fail with a CORS error. | The Static Web App hostname in the APIM CORS policy doesn't match the deployed site. | Compare `staticWebAppHostName` with the policy origin and redeploy the APIM policy. |
| Browser gets `429 Too Many Requests`. | The per-IP rate policy limit was reached. | Wait for the renewal interval; don't treat a client IP as a durable user identity. |
| Copilot MCP connection rejects requests. | The MCP server isn't associated with the expected APIM product, or its connection has the wrong key/header. | Check the MCP server's product/subscription settings and `Ocp-Apim-Subscription-Key` authentication. |
| MCP discovery works but tool content contains `401 missing/invalid subscription key`. | The source REST API still requires a subscription, or the supplied key does not cover it. | Check both resources, product membership, subscription state, and key scope; an MCP `200` is not proof of backend success. |
| MCP returns `invalid_date` for a valid date, or looks up `Barcelona?country=Spain`. | Malformed query parameters in the generated MCP-to-REST request. | Apply the operation-template workaround above and verify actual tool execution. Do not relax Function validation or concatenate qualifiers into the city. |
| Search returns `409 city_ambiguous`. | Multiple places share the requested name. | Use location search and pass `country` or `admin1` with forecast/assessment calls. |
| Search returns no places. | No geocoder result matches the query. | Try a longer spelling or another name; review returned candidates before running a forecast. |
| Weather provider returns `502`. | Open-Meteo was unreachable, timed out, or returned invalid data. | Check Function logs and provider status; verify network access from the Function App. |
| APIM deployment takes a long time or fails. | APIM provisioning is slower than other resources, or the selected region/tier is unavailable. | Inspect Azure deployment operations and current regional availability before retrying. |

## Cleanup

Delete the dedicated resource group after the demo and verify no unrelated resources are included. Never delete a group containing resources outside this sample.

## Publication checklist

- Review tracked files and all branches/tags that will be published, including Git history. An ignore rule does not remove an already committed secret. If one is found, revoke it first, then plan coordinated history cleanup before publication.
- Rotate any APIM or Function key or deployment token exposed outside its credential store. A key shared in chat must be treated as exposed even if it never entered Git. Do not paste replacement keys into issues, prompts, screenshots, or source files.
- Keep `local.settings.json`, real `.env` files, deployment outputs, parameter files with credentials, logs, certificates, and ZIP archives untracked. Keep the lockfiles, example settings, tests, infrastructure, and license: they are needed to reproduce the sample.
- Do not commit raw screenshots. Redact account emails, user details, subscription/tenant IDs, credential values, and live deployment hostnames. Masked key fields are not evidence that every other part of a screenshot is safe. Flatten redactions before sharing; do not rely on an editable overlay.
- Check GitHub issues, pull-request bodies/comments, releases, and other attachments separately; a source-tree scan does not cover them. Review repository Actions secrets, environment settings, and deployment integrations before changing visibility.
- Ensure both the MCP server and source REST API require the intended authentication after diagnostics. Protecting the MCP path alone does not protect its REST API. The separate public web API remains intentionally anonymous and rate-limited.
- Enable GitHub secret scanning and push protection where available. Review cost controls and disable or remove demo deployments when no longer needed. Publishing this repository does not provide a shared hosted service.
